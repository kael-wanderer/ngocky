NgốcKý: improvements and feature proposals

Written 2026-11-15, after a full workspace review and a security and hygiene release (commits 5ec5185 and a63ec5c on main, deployed to production). This is a proposal list for the owner to pick from. Nothing here is decided or scheduled.

1. Context for whoever picks this up

NgốcKý is a family productivity app: an npm-workspaces monorepo with an Express + Prisma + Zod API (apps/api), a React + Vite + Tailwind web app (apps/web), and a Tauri desktop shell (apps/desktop) that runs the API as a bundled sidecar. Production is PostgreSQL on a VPS behind Docker; the desktop app can also run offline on SQLite or against a shared PostgreSQL. A Telegram assistant and reminders run through n8n, or through an in-process scheduler on desktop.

How to work in this repo. Read the repo CLAUDE.md first; it was corrected on 2026-11-15 and is accurate. Typecheck with npm run lint. API tests: npm test -w apps/api (SQLite, isolated). Web tests: npm test -w apps/web. A push to main runs a verify job (typecheck and both suites) and then deploys to production, so never push a half-finished change to main.

State at the time of writing: API 134 tests passing, web 30 passing, both apps typecheck with zero errors.

Two owner rules apply to everything below. A spec for anything with a UI must include an HTML mockup of its screens. Durable documents go under docs/ as self-contained HTML.

Every item below states what was checked in the code. Where it says "not checked", confirm the current state before designing.

3. Improvements to existing features

3.1 Budgets in Expenses

Effort: small to mediumBackend exists
Current state (checked)
The BudgetSetting model and CRUD routes exist at /api/settings/budgets (category, period of weekly, monthly or yearly, amount, active). They gained validation and ownership checks in this release. The web app never calls them: there is no budget screen. Separately, the Alerts page offers a "Budget Exceeded" rule based on a single threshold number, unrelated to these per-category budgets.
Proposal
A budget section in Expenses: set a budget per category and period, and show spent versus budget as a bar per category for the current period. Notify at 80% and at 100%, using the existing alert and notification path. Decide whether the existing threshold alert should be replaced by this or kept alongside.
Things to settle in the spec
Whether a budget covers personal expenses, shared ones, or both (expenses have a scope and an isShared flag). Whether categories come from a fixed list or free text. Amounts are integer VND, formatted with vi-VN; the model currently stores a float.

3.2 Shared confirm dialog and toast messages

Effort: mediumFixes desktop
Current state (checked)
About 45 native dialog calls across roughly 15 pages, no shared confirm component, and no toast library. Errors surface three different ways: alert(), inline state, or not at all.
Proposal
One promise-based confirmDialog() and one toast helper, both styled with the theme CSS variables. Replace every native call. Handlers become async and await the confirmation.
Risk
Wide but mechanical. There are almost no web tests for these pages, so add a test for the dialog itself and check a delete flow on each page by hand, on web and on a desktop build.

3.3 Per-user timezone, end to end

Effort: mediumChanges notification timing
Current state (checked in part)
Users have a timezone field (default Asia/Ho_Chi_Minh) that is only read and written by the Settings page. On the server, day and month boundaries use server-local time, which is UTC in the Docker image, while schedule times use a hardcoded +7 offset. On the web, the "today" defaults in Goals and Healthbook were fixed in this release to use the browser's local date.
Proposal
One server helper that returns start of day, week, month and period for a given user timezone, used by due-notifications, due-reports, goal period rollover and the dashboard buckets. Tests should pin the clock at 23:30 and 00:30 Vietnam time and at a month boundary.

3.4 Reliable notification delivery

Effort: medium
Current state (reported by the review, not re-verified line by line)
The scheduler sends first and marks as sent afterwards. Each poll loads every active goal, open task, calendar event and housework item for all users before checking whether any rule is due.
Proposal
Claim an item before sending, as scheduled reports already do with lastSentAt. Record each attempt (channel, result, error) in a delivery log and show it on the Notifications page. Only load data for rules that are actually due.

3.5 Report export

Effort: small
Current state (checked)
The API has CSV export for tasks and expenses (/api/reports/export/tasks and /export/expenses). The Reports page prints by copying its own HTML into a new window. The unused PDF libraries were removed from the web app in this release.
Proposal
Confirm whether the CSV endpoints are reachable from the UI and add buttons if not. Extend CSV to funds and goals. For PDF, a print stylesheet on the Reports page is cheaper and more faithful than generating a PDF in code.

3.6 Break up the largest pages

Effort: large, can be done one page at a time
Current state (checked)
Reports is about 2,400 lines in one file, Goals 1,700, Healthbook 1,400, Projects and Assets about 1,200 each. The web app has around 400 uses of any.
Proposal
No user-visible change. Split each page into a data hook, a form, and list or detail components before adding features to it. Do this as the first step of whichever feature touches the page, not as a standalone project.

4. New features

4.1 Faster capture through the Telegram assistant

Effort: mediumHighest daily value
Current state (checked)
The assistant already parses intents including create_expense, create_task, goal_checkin, create_health_log, and several queries (apps/api/src/services/assistant/). It uses a language model for parsing with a keyword fallback. The web app has a compact amount parser that understands 45k and 1.2M (apps/web/src/utils/amount.ts); whether the assistant accepts the same shorthand was not checked.
Proposal
Make the short forms dependable without a model call: "cafe 45k" creates an expense, "remind dentist Friday 9am" creates a calendar event with a reminder. Add an undo reply for the last action. Then add receipt photos: the user sends a picture, the model extracts amount, date and merchant, and the user confirms before anything is saved. The pending-action mechanism for confirmation already exists.
Things to settle
Whether calendar event creation is already an intent (not seen in the fallback list). Cost and privacy of sending receipt images to the model provider.

4.2 Recurring expenses and subscriptions

Effort: medium
Current state (checked)
Expense has a recurring boolean that the API accepts, but no code generates the next occurrence; the only uses found are the schema field and its validator. Calendar events and housework already have real repeat logic (repeatFrequency, repeatEndType, repeatUntil).
Proposal
A recurring expense definition (amount, category, frequency, next due date, end date) that creates the expense each period and reminds a set number of days before. A subscriptions view showing monthly and yearly totals. Reuse the repeat fields and enums from calendar events for consistency. Works best together with budgets (3.1).

4.3 Weekly family digest

Effort: small to medium
Current state (checked)
Scheduled reports exist with daily, weekly and monthly frequencies, a plain-text formatter (apps/api/src/services/reportFormatter.ts), and Telegram delivery with duplicate protection.
Proposal
A ready-made report type, one message per person: overdue items, this week's events, housework due, goal progress, and spending against budget. Offer it as a one-click preset on the Scheduled Reports page.

4.4 Global search

Effort: medium
Current state (checked)
No cross-module search endpoint or UI was found.
Proposal
One search box in the layout that queries tasks, project tasks, ideas, learning items, health logs, assets, expenses and calendar events, grouped by module. Every query must apply the same ownership and sharing rules as the module's own list route. A helper for case-insensitive matching across PostgreSQL and SQLite already exists in apps/api/src/config/database.ts.

4.5 Backup and export

Effort: mediumProtects everything else
Current state (checked in part)
No backup code was found in the repo. Whether the VPS has its own backup job outside the repo is not known. Project notes record one disk-full incident on the VPS in July 2026. The desktop SQLite mode has a "reset data" button but no export.
Proposal
Three parts, in this order: a scheduled pg_dump on the VPS with retention and an off-server copy; a per-user "export my data" download as JSON plus uploaded files; a backup and restore button for the desktop SQLite file. Include a written and tested restore procedure, since an untested backup is not a backup.

4.6 Calendar feed for phones

Effort: small
Current state (checked)
No ICS or calendar-feed code was found.
Proposal
A read-only ICS URL per user, with a long random token that can be regenerated, so events appear in the phone's own calendar app. Read-only avoids all two-way sync problems. Hosted mode only; a desktop-only install has no public address.

4.7 Medication and vaccination schedules in Healthbook

Effort: medium
Current state (checked)
Health logs can create a linked calendar event for the next checkup and a linked expense for the cost. There is no concept of a repeating medication or a vaccination plan.
Proposal
Per person: medications with dose, times of day and an end date, and a vaccination list with due dates. Reminders go through the shared notification fields used by other modules. Health data is sensitive, so follow the ownership pattern added in this release and keep reminder text free of medical detail on shared channels.

4.8 Housework rotation

Effort: small to medium
Current state (checked)
Housework items have a single optional assignee and a frequency; completing a recurring item advances its next due date.
Proposal
An optional rotation list per item: on completion, the next person in the list becomes the assignee. A small fairness summary showing completed chores per person per month.

4.9 Installable web app with push notifications

Effort: medium
Current state (checked)
No web manifest or service worker; apps/web/public holds only the logo. The app has a configurable mobile navigation bar, so phone use is clearly intended. Fonts load from Google Fonts, which also means the desktop build needs network for them.
Proposal
Add a manifest and icons so the app can be installed to the home screen, self-host the font, and add web push as a third notification channel next to email and Telegram.
